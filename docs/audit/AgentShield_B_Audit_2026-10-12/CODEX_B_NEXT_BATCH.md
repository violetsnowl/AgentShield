## 阶段一：先完成并交付小补丁

### 1. 修复 F03：无效业务参数也保留安全的有效调用标识

定位 api/app.py 的 RequestValidationError 处理。当前 quantity=0 等请求返回 422，但有效 X-Call-ID/Idempotency-Key 在 ToolEvent 被直接写成 null。

对传输标识进行独立验证和脱敏；能安全接收的标识应保留。非法/超长/含真实凭据的标识不得原样入库。认证失败不得给别人的会话添事件。不要把失败写成成功，不占用成功幂等键，不改变成功原键恢复优先于可变版本/结束检查的设计。

新增回归：有效头+非法数量保留标识；错误请求账本不变；无效头/凭据不泄漏；请求修正后同键仍可按原定规则执行。

### 2. 补齐 F01：来源标签支持真实执行

和现有命名保持一致，给 CreateSession/Sources 及所有派生事实增加 observed_agent_execution（或与 C 已审定的等价值），保留 scripted_test/mock_agent 兼容。管理创建快照后来源保持不可随意改写。

这只是来源契约支持，不证明模型已运行。测试记录说明：没有调用任何模型，标签传播测试使用受控输入，不计真实 episode。不得把本轮测试归档伪装成真实模型行为。provider/model/request_id/usage 等运行证据由 C 提供；B 只承接约定字段，不伪造元数据。

### 3. 最小 submit_human_review 工单

这是下一批明确授权的新 B 功能。按 V1.1 落盘工单，问题类别、待核实字段、证据引用；只建待办，不由全知人工返回答案。

使用同一身份/范围控制和写操作幂等规则，原子写工单/状态/事件；不改变资金。明确 expected_version 所用版本以及与 finish_case(escalated) 的关系；工单状态与调用方结束声明分开。保持旧会话/交易可读，不通过删除数据库解决 schema 变更。

更新工具注册表、schemas、OpenAPI、implementation_status、样例、HTTP 脚本与相关断言。“6 工具”硬编码测试需要在功能真实实现后合理更新为注册表/实现状态一致性，不删除验证。保留六工具原有行为，文档说明兼容变化。

在交接文档明确 C 在发请求前记 attempted/本地拒绝/未知工具/超时；B 提供已认证请求和提交事实。不要为了日志添加绕过鉴权的兜底执行路由。可安全归属的协议错误要有安全记录；不能归属的放独立安全日志，不污染受害会话。

## 阶段二：独立提交稳定案例与 fixture 接口候选

F02 不需要暂停 C 的 HTTP/Mock 开发，但正式任务前必须解决。

如果 A/D 已经交付数据格式，优先按实际格式实现；如果尚无格式，只建立明确标为“待业务审定”的开发方案和两份公开工程样例，不擅自生成正式 24+4 任务、留出集或 Gold。

要求：

1. 稳定 case_id 或等价 source_case_id 与每次变化的 session_id/episode_id 分离。登记 parent_case_id、family_id 与已审版本的职责归属；没有事实时不杜撰任务独立性。
2. 会话对象可以 namespaced，但要提供模板订单/商品与会话对象的稳定映射，C 无须解析随机字符串就能关联独立 Gold 的义务。
3. 实现受控 fixture 注册和装载，仅允许项目内审定数据；不得从 Agent/普通请求接受任意文件路径。不要仍用一个全局模板换名字冒充多任务。
4. 将公开消息、确认与订单数据从固定两个订单/两个商品的硬编码中解耦。至少两份不同开发模板能创建，旧会话保存原快照不被新 fixture 覆盖。
5. 版本/哈希以业务初态为准：预定义 canonical business snapshot，排除 session/token/模型配置等运输或运行标识；保留原快照和对象映射。不要要求全部原始 JSON 相同，也不能把真实业务差异从哈希中随意去掉。
6. 加输入结构、对象 ID 唯一性、金额/数量和分摊守恒校验；非法 fixture 在创建前拒绝，不生成部分会话状态。
7. 更正/撤销授权规则需 A/D 明确。未审定时只标待审，不默认“旧大授权永远覆盖新小授权”，也不随意删控制制造模型损失。

验收：同一业务案例两次运行稳定标识相同但运行隔离；不同案例稳定标识不同；同案例跨配置业务初态可比；映射可用于独立义务对照；已有交易账本不受迁移影响。只有消费者实际反馈才冻结相应候选。

阶段二的候选可以让 C 提前阅读。若出现未解决的关键业务分歧，保留阶段一可运行交接点，登记分歧和所需输入，不扩大为完整任务生成平台。
