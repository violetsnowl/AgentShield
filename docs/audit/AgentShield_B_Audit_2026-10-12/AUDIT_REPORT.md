## 3. 值得保留的实现

### 3.1 数据库确实有事务，不是只做了接口外观

`sandbox/store.py:46–57, 169–260` 将退款、账本、快照更新、成功幂等记录和提交事件放在同一事务中。现有故障注入和本次多行补测均验证了回滚；同键恢复先于可变版本/已结束状态检查，避免已成功请求重试被错误当作新退款。

SQLite 官方对 BEGIN IMMEDIATE 的说明与这里的串行写入设计一致，但“用了事务”本身不构成正确性证明，仍以实际断言为准。[O1]

### 3.2 C 可以不导入 B 的内部业务函数

标准库 `scripts/bc_smoke_test.py` 通过 HTTP 完成读取、退款、恢复与证据检查。管理凭据负责建会话/读证据，会话凭据负责 Agent 工具调用；模型不应得到其中任何凭据。管理只读 EvidenceBundle 有初始和最终快照、退款、账本、事件，不把损失/赔款或正确答案伪装为 B 的事实。

### 3.3 一条等价双向账本不等于少记了一边

`LedgerEntry` 同时保存 merchant_delta 和 customer_delta；测试核对二者和为零。333 分退款只有一条此类账本是当前等价守恒设计，不能仅因不是两行分录就判错。

### 3.4 范围控制和完成状态诚实

代码与文档明确 6 工具 implemented、人工工单 planned；没有假模型、假保险接口、假正式结果。B 首批提示词第 4 节原本只要求六个核心工具，人工工单允许随后补充。因此它未实现**不是违反首批任务**，但下一阶段确实需要补。

## 4. 发现与处置级别

这里区分“已实现路径缺陷”与“原本尚未实现的扩展条件”，不把所有计划内缺项都叫严重 Bug。

### F01｜真实执行来源尚未支持：接真实模型前补齐

**类型：下一阶段接口缺口，不是首批金额漏洞。**

位置：`contracts/models.py:25–38`。

Sources 和 CreateSession 的 execution_source 只允许 scripted_test / mock_agent。本次向创建会话接口发送 `observed_agent_execution`，返回 422。见 `probes.json/P01_real_execution_source`。

后果：C 的模型技术上可以调用六工具，但 B 的正式事实无法按当前契约诚实标记其真实执行来源。不能为了跑通而把实际模型运行永久记成 scripted_test，也不能事后直接改旧轨迹来源。

建议：B/C 约定真实执行来源值并贯通创建、快照、事件、EvidenceBundle 与 schema；保留旧枚举兼容。标签本身不证明实际模型执行，C 还必须保存实际提供商、模型、请求及用量等可用记录，缺失元数据记 null。变更后继续保持 B 不调用付费 API。

验收：相应来源的会话创建成功，所有事实标签一致；旧脚本/Mock 不被自动改标；未运行模型的测试明确属于标签传播测试，不宣称获得真实执行证据。

### F02｜任务模板和运行实例未分离：正式任务接入与接口冻结前补齐

**类型：开发模板局限；会影响任务聚合、Gold 对照及公平比较。**

位置：`contracts/models.py:33–38, 41–53`；`sandbox/fixture.py:6, 26–66`。

目前只接受 dev-refund-v1；另一个 fixture_id 返回 422。每次创建会话都会把 case_id、订单/商品/消息 ID 重新拼接为当前 session 的 ID；重复同一模板运行时 case_id 也不同。当前未见稳定案例、parent/family 或运行对象到模板对象的明确映射。消息生成还写死了“第一订单两商品、第二订单一商品”的开发结构，不能简单增加一个 JSON 文件就称已支持任务库。

复现：`probes.json/P02_second_fixture`、`P03_repeated_case_identity`。

需要区分：

- **稳定案例标识**：同一业务案例跨重复/跨配置保持不变，Gold 与分类据此关联。
- **运行标识**：session_id、episode_id 每次不同，保证状态隔离。
- **对象映射**：会话内订单 ID 可以不同，但应有稳定模板订单/商品标识或等价映射，供 C 对照义务。

建议：增加受控 fixture 注册/装载机制，仅从项目内审定目录加载，不接受任意文件路径；将公开消息、订单和资格从硬编码解耦。至少用两个不同开发模板验证功能，不由 B 编造正式 24+4 任务或 Gold。case/parent/family、fixture/policy/environment 版本和可比业务状态哈希的具体字段由 A/B/C/D 候选审定。

公平性验收不能要求含 session/token/config 的整个快照逐字相等；应约定 canonical business snapshot，只对业务条件计算哈希，排除预登记的运行标识，同时保留映射与原始快照。

验收：同一案例两次运行——稳定案例相同、运行标识不同、业务初态可比；不同案例有不同稳定标识；会话之间仍不能越权；对照 Gold 不必解析随机字符串猜来源。新 fixture 做结构/金额一致性验证，拒绝重复对象 ID 或不守恒的分摊。

### F03｜参数校验失败时丢失有效调用标识：建议下一补丁修复

**类型：已实现错误路径的可追溯性缺陷；不产生重复扣款。**

位置：`api/app.py:87–96`。validation_error 明确把 call_id、key 写为 None。

复现：发送 quantity=0，HTTP 头给出有效 `X-Call-ID: audit-invalid-call` 和 `Idempotency-Key: audit-invalid-key`。返回 422，ToolEvent 中两个字段却都是 null；request_id 仍能对应。见 `probes.json/P04_invalid_request_correlation`。

后果：不能直接按模型工具调用 ID 关联这次无效请求；C 可以靠 request_id 自行补关联，但不应无故丢掉已收到的有效元数据。

建议：独立验证安全传输标识，参数错误时也保留有效且不含凭据的 call_id/幂等键。无效、超长或复用真实凭据的头不得原样入库；失败不得占用成功幂等键。FastAPI 可通过 RequestValidationError 和 Request 处理相应信息，注意不要把未经清洗的原始 body/凭据直接返回或入日志。[O2]

验收：有效头＋非法业务参数→422、无资金改变、事件保留标识；无效头→安全拒绝；凭据不落入事实；既有幂等恢复逻辑不变。

### F04｜未知工具/损坏 JSON 没有会话 ToolEvent：补充运行器侧留痕约定

**类型：观测覆盖边界，B/C 共同处理。**

复现：合法会话令牌向不存在工具发请求，404、会话事件数不增；损坏 JSON 返回 422、事件数也不增。见 `probes.json/P06_unknown_tool_audit`、`P08_malformed_json_audit`。

不能据此说真实交易漏账：这些请求都未形成交易。但如果只看 B 的 ToolEvent，会漏掉部分工具尝试。

建议：C 在发出 HTTP 请求之前保存 attempted 记录，记录本地参数拒绝、未知工具、请求/响应/超时等。B 对能够安全认证的错误请求尽量保留安全审计；无法归属的请求进入独立安全日志而不是污染他人会话。B 事件不必承担运行器根本没有发出的调用，C 的尝试也不能冒充已提交资金后果。

最低验收：C 能追踪一次未知工具尝试、一次无效参数与一次超时，管理端完整记录可以区分它们与已提交退款；不要为审计放宽鉴权或开放万能工具路由。

### F05｜人工工单未实现：完整三场景开发验证前补齐

**类型：首批明确允许的 planned 功能。**

位置：`contracts/models.py:93–96, 256–265`。

submit_human_review 返回 404；finish_case(outcome=escalated) 返回 finished，但只是声明，没有创建工单。原文已写清，并非偷偷假装实现。见 `probes.json/P07_human_review`。

下一批实现最小持久工单，按 V1.1 只登记问题、待核实字段和证据，不提供全知人工答案。确定会话版本、幂等及结束规则；工单不移动资金。加入当前工具列表后更新测试中的“固定六工具”断言——应检查审定注册表与实现状态，而不是偷偷删掉覆盖。

## 5. A 的业务审查仍不可省

开发 fixture 同时放了较宽“甲三件乙两件全退”和较窄“甲累计一件”的确认。当前按引用确认单独执行，代码没有消息撤销/更正语义，文档也承认这一点。

不能未经业务审定就判这是漏洞，也不能默认它足以代表真实售后更正。A/D 需要明确当前意图、消息顺序、授权替代/撤销规则。语义不明确时允许转人工。不得为了让 Agent 产生损失而删除本来存在的结构化确认或普通支付控制。

分摊算法在当前手算/测试中能守恒，但正式业务规则采用什么尾差和授权定义仍须 A/D 审定。工程模板没有对应完整正式 Gold，不能对其自然损失或保险责任下结论。

## 7. 保留到以后，不要现在重写

不要为了此审计改成微服务、PostgreSQL、通用插件、真实支付、复杂鉴权平台或性能工程。当前小规模本机队列场景下，已有 SQLite 实现值得保留。吞吐、完整多机部署、令牌轮换和生产安全不在这次验收结论内。

更不应因为 26 项测试通过就推断整个保险系统已接近完成：已经打通的是一个交易开发模板；正式任务、模型、独立核验、保险、前端和材料仍按分工推进。

## 8. 最终判断

**可以交接 B，可以让 C 现在开始接入，不必推倒重写；但先解决真实来源、稳定案例/fixture 和错误追溯问题，再通过人工工单补齐完整开发场景，才进入正式任务实验。**

本次未发现已复现的重复退款、金额不守恒或跨会话成功越权；这个限定结果不是对所有输入、配置及未来改动的安全保证。
