## 3. 值得保留的实现

### 3.1 前端显示的确实是 B 的模拟业务事实

`seed_development` 经 B HTTP 产生 333/250 分开发退款，而不是在 React 写死成绩。读取、原键重放和工单与资金提交分开。新建开发会话只建初态，不暗中执行 Agent。风险和合同区没有伪造 A/C 结果。

这些是“真实执行了开发脚本、产生模拟交易”，不是实际模型实验或现实退款。

### 3.2 观察者不是把管理员令牌直接发给浏览器

`workbench/app.py`：一次性启动授权换取独立 HttpOnly cookie；B 管理凭据只在服务端 HTTP 客户端；路由和租户限定；创建响应丢弃 session_token；无任意目标代理。Host、Origin、请求头、授权、退出、只读不变等路径经过回归及补测。

这是受限的可信本机开发方案，不是公开部署认证。不能直接把监听地址改成 0.0.0.0 后宣布可给所有队友访问，也不能把“浏览器有观察者 cookie”误说成“B 管理员凭据泄露”。

### 3.3 没有用放宽安全约束解决构建问题

源码已采用提交的预编译 JSON Schema 校验器；CSP 不包含 unsafe-eval。用户保留了中间失败日志。原交易、幂等、工单和历史事实没有因前端施工被重写。

### 3.4 旧证据与未知状态得到显式处理

schema 1/2/3、legacy_unavailable/null、旧工单集合缺失和空数组分开。来源标签不作为真实模型证明。这些已有处理应当在修复时保留。

## 4. 发现 F03-01：回放解析只校验部分结构，没有检查资金记录之间的一致性

**优先级：P1，建议作为 04 的第一项修复。影响证据展示可信度，不是已复现的 B 资金漏洞。**

位置：`frontend/src/data.ts:11–49`；显示位置 `frontend/src/App.tsx:55–75`。

当前正确拒绝了混合 session、重复 seq/交易和不安全整数，但以下数据仍被 parseEvidence 接受：

1. 只把实际样例 `refunds[0].amount_cents` 从 333 改为 99999，退款商品行、账本及最终余额仍是原来的 333 分。
2. 把账本客户增量由 +333 改为 +999，商户增量仍为 -333。
3. 保留退款，删除全部账本条目。
4. 把账本 transaction_id 改为与退款不对应的合法 ID。
5. 改变 final_snapshot.case.case_id 或 final_snapshot.session.tenant_id，使内部身份不一致。
6. 修改 canonical_initial.case.request，但保留旧 business_initial_hash。

前四项会让当前显示代码存在“总退款来自 refunds，但账本/余额来自另一套矛盾值”的可能。第 3/4 项点开追溯时已有局部缺失提示，不能说完全毫无警告；但页面汇总、无资金空状态和“守恒账本”等措辞仍没有统一的一致性状态。第 6 项是校验层级的缺口，不证明 hash 应当被当作签名。

### 复现证据强度

`frontend_logic_probes.cjs` 转译并运行提交的原 data.ts，以及提交的预编译 validator。由于 npm 不可用，使用容器 TypeScript 5.8.3，Ajv 的唯一 ucs2length 运行时助手由 `Array.from(s).length` 替代；不是锁定依赖的整套前端测试。未修改业务源码。上述变更与其余控制样例均在该条件下执行，原始对象仍可通过，混合 session/重复退款/不安全金额被拒绝。

### 建议修法与验收

- 区分结构校验、可验证的内部一致性、来源真实性。未签名不代表可以把已发现的算术矛盾当普通数据展示；校验通过也不能声称来源真实。
- 对 schema/已记录字段确能验证的内容，检查退款总额与商品行小计、退款与账本交易关联、双边增量及期初期末余额等基本恒等关系。不复制 B 退款决策算法，不计算 C 损失或 A 赔款。
- 明确冲突时拒绝进入正常可信视图或醒目标记损坏；历史资料确实缺失时保留 unknown/not_verified，不自动补零、不伪造映射，不把所有旧证据一概拒绝。
- 对 recorded 的 canonical 初态，可以按已审定的 B 序列化规则复算 hash；暂不复算时标为“文件声明值／未复核”。两者都不能冒充签名或现实来源证明。
- 使用原 15 项测试之外的变更算例，在真实 Vitest 与浏览器导入操作中补回归。与跨语言金额/哈希规则有关的字段由 B/C 审核，不擅自改契约含义。

## 5. 发现 F03-02：创建会话的迟到响应可以覆盖刚导入的回放

**优先级：P1，04 开头补真实浏览器回归后修复。不是重复退款或越权。**

位置：`frontend/src/App.tsx:143–147, 163–170, 185–187`。

操作顺序：点“创建开发会话”并延迟其 HTTP 返回 → 页面仍允许“导入回放” → 成功导入另一份合法的 v2 证据 → 原创建响应抵达。

`create()` 在 await 后不检查用户是否已经切到本地回放，继续 `await catalog(); setOffline(false); setBundle(null); setSid(新会话); setArea('lab')`。这会抢走刚选择的回放，并重新查询本机目录。普通读取请求的 AbortController 和更多事件的 selection 检查没有覆盖该处理函数。

`frontend_async_probe.cjs` 对提交 App.tsx 做处理函数级转译，使用最小 hook 存储和可控网络完成顺序；观察到 offline=true/合法回放 session 被迟到响应改为 offline=false/新建 session。该 harness 不是完整 React 或浏览器实测，因此正式修复前须用项目 Playwright 在原环境复现；导入使用仓库已有的合法 v2 文件，而非混合 ID 的无效文件。

### 可接受的修法

最小方案是创建过程中禁用冲突的导入入口并解释；或用统一交互序号/模式检查，保证已开始但迟到的操作不会覆盖较新的用户选择。异步文件读取和返回本机模式也应有一致的处理边界。

不得以删除已创建的服务端会话来撤回 UI 操作。取消等待不证明创建未发生；仍保留现有“响应丢失先核对目录”的提示。真实浏览器验证延迟创建→导入/禁用→释放响应、连续文件选择、退出回放，以及原有快速切换 session 的行为。
